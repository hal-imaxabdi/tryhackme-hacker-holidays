DOOR 08 Web Exploitation Medium

Towel on the sunbed

Summary

Ponzi Portfolio is a crypto-rewards web app that lets users claim a staking reward once every 24 hours. Reaching a balance of 150 PONZI unlocks the "Whale Vault," which contains the flag. The claim endpoint suffered from a classic TOCTOU (time-of-check to time-of-use) race condition: the check for "has this user already claimed today?" and the write that records the claim were not atomic. Firing multiple concurrent requests at the endpoint let several of them pass the check before any of them updated the claimed state, granting far more than the intended 50 PONZI per day and bypassing the 24-hour cooldown entirely.

Target

  • App: http://10.48.133.85:3000 - "Ponzi Portfolio: Stack your bags. Claim your yield."
  • Auth: session cookie (connect.sid), Express backend

Recon

Registered a guest account and logged in:

POST /auth/register
{"username":"hacker1","password":"password123"}

The dashboard showed:

  • Portfolio Balance: 0 PONZI, tier "Shrimp"
  • Staking Rewards: "Earn 50 PONZI every 24 hours by claiming your reward" → Claim Reward button
  • Whale Vault: "Reach 150 PONZI to unlock the Whale Vault and claim your exclusive reward"

Identifying the vulnerable endpoint

Clicking Claim Reward with Burp Suite's proxy intercepting traffic revealed:

POST /claim HTTP/1.1

Host: 10.48.133.85:3000

Cookie: connect.sid=<session>

Response (first claim):

{

"message": "Staking reward claimed successfully.",

"reward": 50,

"newBalance": 50,

"tier": "Shrimp",

"priceSnapshot": 4.2

}

A second immediate claim attempt returned:

{

"error": "Reward already claimed. Please wait before claiming again.",

"secondsRemaining": 85861

}

This confirmed the 24-hour cooldown is enforced server-side, not just by disabling a button client-side. The /dashboard/api/me endpoint also reported canClaim and secondsUntilClaim, and whaleThreshold: 150, confirming the target balance needed for the vault.

Hypothesis: race condition on first claim

The claim response contains no timestamp fields returned to the client, and the cooldown re-appeared instantly after a single claim - consistent with server logic along the lines of:

1. look up user's lastClaimAt

2. if now - lastClaimAt < 24h → reject

3. otherwise: credit reward, set lastClaimAt = now

If steps 1–3 are not wrapped in an atomic transaction/lock, sending many /claim requests at the same instant, on a session that has never claimed, could let multiple requests pass step 2 before any of them completes step 3 - because each one still sees "no prior claim" when it performs its check.

Testing this against an account with an already active cooldown predictably failed - the server correctly rejected all parallel attempts with 429/"already claimed", since that state had already been committed. The exploitable window is specifically the very first claim on a fresh account, before any "claimed" state exists to race against.

Exploitation

  1. Registered a brand-new account and logged in without clicking "Claim Reward" in the browser, so no claim state existed yet server-side.
  2. Sent the /claim request to Burp Repeater and duplicated it into a group of identical requests, all carrying the new account's session cookie.
  3. Used Burp Pro's "Send group (parallel)" feature, which dispatches all requests in the group at effectively the same instant.
  4. Result: several of the parallel requests returned 200 with "Staking reward claimed successfully", each reporting an incrementing balance:
{"message":"Staking reward claimed successfully.","reward":50,"newBalance":50, ...}
{"message":"Staking reward claimed successfully.","reward":50,"newBalance":100, ...}
{"message":"Staking reward claimed successfully.","reward":50,"newBalance":150, ...}
{"message":"Staking reward claimed successfully.","reward":50,"newBalance":200, ...}
{"message":"Staking reward claimed successfully.","reward":50,"newBalance":250, ...}

while a couple of the later-arriving requests correctly received "Reward already claimed", showing the race window was narrow but real.

  1. Refreshed the dashboard: 250 / 150 PONZI, tier upgraded to Whale, and the Open Vault button was now enabled.
  2. Clicked Open Vault, and the flag was displayed directly in the Whale Vault panel:
THM{t0w3l_0n_th3_sunb3d_d0ubl3_sp3nt}

Root cause

The claim-processing logic performed a read-check-write sequence against the user's claim state without any locking, mutex, atomic increment, or database-level transaction/constraint (e.g. a conditional UPDATE ... WHERE last_claim_at <= now() - interval '24 hours' checked via affected row count). This allowed concurrent requests to all read the same "not yet claimed" state and all proceed to credit the reward independently.

Remediation

Perform the check-and-update as a single atomic database operation, e.g.:

UPDATE users

SET balance = balance + 50, last_claim_at = NOW()

WHERE id = :user_id AND last_claim_at <= NOW() - INTERVAL '24 hours'

RETURNING *;

  • and only credit the reward if the update affected exactly one row.
  • Alternatively, use a per-user lock (e.g. a Redis SETNX/distributed lock, or a DB row-level lock via SELECT ... FOR UPDATE) around the entire check-then-write sequence so concurrent requests are serialized.
  • Rate-limit the claim endpoint per session/IP as defense in depth.
